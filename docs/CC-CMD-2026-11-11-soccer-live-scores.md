## Design

The live fact lives in ESPN, reached through `/v2/games`. The archive (`/context/date`, cached 300 s, written final-gated by a `*/15` tick) is the wrong channel for a live card, and a relay write of an in-play score into it would stamp `finalized_at` and render `Final` mid-match. So:

- **The lab joins `/v2/games` onto the row it already has**, by `EspnEventId`, in a pure function `applyLive`. It merges `home.score` and `away.score` only when the feed state is `live` or `final`, never from `pre`, and **never sets `FinalizedAt`**. `gameStateAt` is unchanged and no fourth `GameState` case is added. *(As built: the join is the poll's, by ESPN event id; the merge is `LiveScore.foldReading`, folded inside the card over its own state signal. Pick'em and Stats read the archive row alone and do not see a reading, so for the minutes a match is in play the card says `In progress` where the Pick'em chip says `PENDING`; this paragraph first said the three "keep agreeing", which was the intent and not what was built, found by review 2026-11-11. The parity is `docs/CC-CMD-2026-11-11-live-scores-tabs.md`.)*
- **Full time:** feed `final` with no `finalized_at` on the row, and `Final` not yet true, shows `In progress` with a `Full time` marker. `Final` arrives only from the archive.
- **A started row with no served score** reads a named status, never `Scheduled <iso>`. Built as `Start time passed, no score served` (CC's wording; the owner may change it). It says what is known: a postponed fixture is also a row whose start time has passed and that has no score, so `Kicked off` would be a claim the row does not support. Pre-kickoff text is unchanged byte for byte.
- **If the feed fails or has no match for the card:** a named state (proposed `live score unavailable`), never `—` and `Scheduled`. No fallback to a capture.
- **Stats:** `Stats.liveMargin` has no sport gate, so once a soccer row is `InProgress` the Stats tab would print baseball wording (`N-run gap`, `needs an inning`). It is gated to non-soccer first (Task 3).
- **The poll, as conditions (CC's proposal, for the owner to change):** `LIVE_POLL_MS = 60000`; a card is *in window* from its kickoff to kickoff + 3 h; the poll runs only while at least one soccer card is in window and `document.visibilityState === 'visible'`, and stops otherwise; one `GET /v2/games?sport=<key>&date=<ET field day>` per lab soccer key that has a card in window per tick (one key on the EPL matchday). Arithmetic (Rule 78): a viewer's 3 h window is 180 requests per key; each live request costs the relay one uncached BSD call and one `GameDO /wp` write (fact 6) and `AmbientDO` already makes 720 of them per key per 3 h, so one viewer adds 25% and ten add 250% to the relay's `/v2/games` load for that match. That is the reason for 60 s and for the visibility gate. A relay-side `cf` cache on the BSD call would cut it and is relay-directed (Task 11).
- **Reader refresh remains:** the Today button re-runs `start()`.
