# Merging the 51 MLS pairs — dry run first

`scripts/merge-mls-duplicate-pairs.mjs`. **Dry run is the default**; a write
needs `--execute --i-have-approval`, both flags, plus a separately-typed
workflow phase.

## A merge is not a delete, and treating it as one loses data

Each side holds fields the other lacks. The dash row carries `venue` and
`opening_odds` and no `espn_event_id`; the underscore row carries the event id
and the start time. So the survivor **absorbs every field it is missing** before
the loser goes, and no non-null value on the survivor is ever overwritten — there
is no undo on a D1 write, and the loser is the stub.

## Survivor rule, and the four refusals

The `provider-composite` row survives — the shape this project writes, and the
shape `briefs.game_id` is most likely to reference. When it lacks the event id,
the merge supplies the slate's.

`pickSurvivor` refuses rather than guesses in four cases:

| refusal | why it must refuse |
|---|---|
| two different non-null event ids | that is two games; merging destroys a real fixture |
| an event id contradicting the slate | merging onto a key the source disagrees with invents the answer |
| no slate key | nothing authoritative to merge onto |
| not exactly one `provider-composite` row | two of our own rows is one writer running twice — a different defect this merge does not address |

None of these can fire given the resolve run said `one-fixture` on all 51. They
are checked anyway: **a gate earns its place by holding when the reasoning
upstream of it is wrong.**

## Ids are not renamed, and that is a decision

`briefs.game_id` joins on the games id — that is what `game-id-scheme.mjs` exists
to classify. Renaming a survivor to the `${SPORT}_${date}_e${eventId}` shape
`d253209` now writes would orphan every brief pointing at it. Out of scope, and
named here so it is a decision rather than an omission.

## What the dry run reports, and what blocks

Per pair: the survivor, the loser, the merge key, the exact fields the survivor
would absorb, and how many `briefs` and `change_log` rows reference the row that
would be deleted.

Six gates, and any failure blocks the execute path from inside the script — not
only from the workflow:

1. there is a plan to act on (zero pairs is a finding, not a clean merge)
2. no pair was refused
3. no brief references a row that would be deleted
4. no `change_log` row does either
5. every merge key is distinct — two pairs on one event id would fold two real
   fixtures together
6. every survivor is distinct

## Execution verifies, it does not assume

After each pair: the loser row is counted to confirm it is gone, and the survivor
is re-read to confirm it is present with its event id. Both facts, both checked,
per pair.

## Teeth

16/16 self-tests, and every gate proven by mutation:

| mutation | result |
|---|---|
| two-different-event-ids gate removed | 15/16 |
| slate-key contradiction gate removed | 15/16 |
| provider-composite uniqueness gate removed | 14/16 |
| no-slate-key gate removed | 15/16 |
| `mergePayload` overwrites a non-null survivor | 15/16 |
| `created_at` becomes mergeable | 15/16 |

**The first one passed 16/16 until the test was fixed.** With two differing ids
and a slate key present, at most one id can equal the key — so the
slate-contradiction gate refuses that input too, and a test asserting only
`refuse === true` passed with the gate deleted. The assertion now checks the
*reason*, because the gate earns its place by firing first and saying "two
games" rather than "the key disagrees". Every refusal test now asserts its own
cause for the same reason.

That mutation run also had to be redone: the first attempt drove `sed` through a
shell that ate the `&&`, three anchors matched zero times, and the unmutated file
honestly reported 16/16 three times. The runner now asserts the file changed
before believing the count — the same failure this session already found once in
a different mutation harness.
