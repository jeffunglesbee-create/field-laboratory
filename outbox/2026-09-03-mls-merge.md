# Merging the 51 MLS pairs — dry run first

`scripts/merge-mls-duplicate-pairs.mjs`. **Dry run is the default**; a write
needs `--execute --i-have-approval`, both flags, plus a separately-typed
workflow phase.

## A merge is not a delete, and treating it as one loses data

Each side holds fields the other lacks. The dash row carries `venue` and
`opening_odds` and no `espn_event_id`; the underscore row carries the event id
and the start time. So the survivor **absorbs every field it is missing** before
the loser goes, and no non-null value on the survivor is ever overwritten — there
is no undo on a D1 write, and the loser is the stub.

## Survivor rule, and the four refusals

The `provider-composite` row survives — the shape this project writes, and the
shape `briefs.game_id` is most likely to reference. When it lacks the event id,
the merge supplies the slate's.

`pickSurvivor` refuses rather than guesses in four cases:

| refusal | why it must refuse |
|---|---|
| two different non-null event ids | that is two games; merging destroys a real fixture |
| an event id contradicting the slate | merging onto a key the source disagrees with invents the answer |
| no slate key | nothing authoritative to merge onto |
| not exactly one `provider-composite` row | two of our own rows is one writer running twice — a different defect this merge does not address |

None of these can fire given the resolve run said `one-fixture` on all 51. They
are checked anyway: **a gate earns its place by holding when the reasoning
upstream of it is wrong.**

## Ids are not renamed, and that is a decision

`briefs.game_id` joins on the games id — that is what `game-id-scheme.mjs` exists
to classify. Renaming a survivor to the `${SPORT}_${date}_e${eventId}` shape
`d253209` now writes would orphan every brief pointing at it. Out of scope, and
named here so it is a decision rather than an omission.

## What the dry run reports, and what blocks

Per pair: the survivor, the loser, the merge key, the exact fields the survivor
would absorb, and how many `briefs` and `change_log` rows reference the row that
would be deleted.

Six gates, and any failure blocks the execute path from inside the script — not
only from the workflow:

1. there is a plan to act on (zero pairs is a finding, not a clean merge)
2. no pair was refused
3. no brief references a row that would be deleted
4. no `change_log` row does either
5. every merge key is distinct — two pairs on one event id would fold two real
   fixtures together
6. every survivor is distinct

## Execution verifies, it does not assume

After each pair: the loser row is counted to confirm it is gone, and the survivor
is re-read to confirm it is present with its event id. Both facts, both checked,
per pair.

## Teeth

16/16 self-tests, and every gate proven by mutation:

| mutation | result |
|---|---|
| two-different-event-ids gate removed | 15/16 |
| slate-key contradiction gate removed | 15/16 |
| provider-composite uniqueness gate removed | 14/16 |
| no-slate-key gate removed | 15/16 |
| `mergePayload` overwrites a non-null survivor | 15/16 |
| `created_at` becomes mergeable | 15/16 |

**The first one passed 16/16 until the test was fixed.** With two differing ids
and a slate key present, at most one id can equal the key — so the
slate-contradiction gate refuses that input too, and a test asserting only
`refuse === true` passed with the gate deleted. The assertion now checks the
*reason*, because the gate earns its place by firing first and saying "two
games" rather than "the key disagrees". Every refusal test now asserts its own
cause for the same reason.

That mutation run also had to be redone: the first attempt drove `sed` through a
shell that ate the `&&`, three anchors matched zero times, and the unmutated file
honestly reported 16/16 three times. The runner now asserts the file changed
before believing the count — the same failure this session already found once in
a different mutation harness.

## Result — the dry run blocked, which is what it is for

Run `33782653151`. **51 planned, 0 refused, nothing written**, and gate 4 failed:

```
losers with briefs: 0
losers with change_log: 47
distinct keys: 51 of 51   distinct survivors: 51 of 51
absorb counts: {'opening_odds': 4}
```

**47 of the 51 rows that would be deleted are referenced by a `change_log` row.**
Deleting them orphans an audit trail. No brief is affected.

Two smaller facts worth keeping:

- **Only 4 pairs would absorb anything**, and it is `opening_odds` in all four.
  `venue` agreed on 46 and the survivor already holds it, and `espn_event_id`
  never appears in a payload — every one of the 51 survivors already carries the
  event id. The merge is small in data terms and the survivors are already
  keyed the way `d253209` writes.
- 51 distinct keys and 51 distinct survivors, so no merge could fold two
  fixtures together.

### And a defect of mine the block exposed

The referential check named `briefs` and `change_log` **because those were the
two tables I could name.** That is the guess-instead-of-probe this repo keeps
deleting, and it would have passed silently if the orphans had been in a third
table.

Fixed: the referencing columns are now **discovered** from `PRAGMA table_info`
over every table `/d1/execute` allows, matching `game_id` and `*_game_id`. A
table nobody remembered now blocks. A new gate asserts at least one referencing
column was found, because zero would mean the check measured nothing and would
read exactly like a clean merge.

The dry run also now prints a **sample of the actual referencing rows**, not just
a count. Whether a `change_log` row should be repointed at the survivor, left, or
treated as disposable is a decision that needs the content — and reading it off a
count is the same error twice more.

## Second dry run — discovery found a THIRD table, and the sample changed the plan

Run `33782906928`.

```
  referencing column(s) discovered: change_log.game_id, odds_history.game_id,
                                    briefs.game_id, ...

  rows in other tables pointing at a row that would be deleted:
     135  change_log.game_id
      22  odds_history.game_id
```

**`odds_history.game_id` — 22 rows — is a table I never named.** The original
two-table check would have deleted all 22 references silently. That is the fix
paying for itself on its first run.

And the sample changed the plan rather than confirming it:

```json
change_log: {"id":10467,"game_id":"2026-08-29-mls-sd-la","source":"odds_api",
             "field":"opening_odds","old_value":null,
             "new_value":"{...draftkings...captured_at 2026-08-29T10:01:46...}"}
```

**The odds pipeline wrote to the DASH row.** 135 change_log rows and 22
odds_history rows are a real odds series hanging off the rows that would be
deleted — not incidental bookkeeping. Deleting them detaches that series from the
fixture it belongs to.

## So the merge repoints rather than orphans

The fixture survives under the other id — the slate established that — so the
references move onto the survivor:

```sql
UPDATE change_log    SET game_id = <survivor> WHERE game_id = <loser>;
UPDATE odds_history  SET game_id = <survivor> WHERE game_id = <loser>;
```

**Order is not arbitrary.** Repoint, verify zero rows still point at the loser,
then merge fields, then delete. Repointing first means a failure leaves the row
in place to try again; deleting first would leave 157 references pointing at
nothing with no way back. The repoint verifies per table per pair and **throws
rather than proceeding to the delete**.

Two new gates:

- every referencing table is writable through `/d1/execute` — a delete that
  cannot repoint must not run
- pairs where **both** rows carry references in the same table are printed in
  full, because repointing there merges two series into one and that is a
  judgement, not a mechanical step

Post-execution now verifies three facts per pair, not two: the loser is gone, the
survivor is present, **and nothing still points at the deleted row**.

## Blast radius, stated plainly

This is no longer "delete 51 rows". It is:

| action | rows |
|---|---|
| repoint `change_log.game_id` | 135 |
| repoint `odds_history.game_id` | 22 |
| `UPDATE` a survivor's `opening_odds` | 4 |
| `DELETE` a duplicate row | 51 |

**212 rows across 3 tables.** The dry run exists so that number is read before it
is executed rather than after.
