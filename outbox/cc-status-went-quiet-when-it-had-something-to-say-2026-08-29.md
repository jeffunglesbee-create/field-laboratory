# STATUS.md went quiet at the moment it had something to say

**Date:** 2026-08-29
**Scope:** `.github/workflows/status.yml`

## The chain, and where it breaks

`STATUS.md`'s first line answers the question this repo kept asking out loud:

```
## Did the suite pass on main?

**green** on `42e793d`
```

It is generated by `status.yml`, which fired on:

```yaml
workflows: [deploy, pages, drift-sentinel]
```

`deploy` fires on **verify success**. `status` fires on `deploy`. So the chain
that keeps that line current runs only when the answer is *yes*.

On a red verify: deploy never runs, status never runs, and the line keeps
reporting the last green commit until the daily 06:33 backstop — up to
**24 hours** later. The file that exists to answer "is main green" goes stale
precisely when the answer changes to no.

## Measured, not hypothesised

`verify` was red on three consecutive commits today — `64ac887`, `4b00a5b`,
`c338742` — each failure blocking the deploy. The question "is main green" was
answered by hand from run logs each time, roughly ten times across the session.

That hand-reading is exactly what this workflow's own header says it exists to
end:

> It exists because that question kept being asked out loud — is the page up,
> did the secret land, has the sentinel found anything — and answering it meant
> opening run logs. Now the repo answers it.

It answers it, except on failure.

## Fix, and why it is gated

`verify` is added to the trigger list, and the job carries a condition:

```yaml
if: >-
  github.event_name != 'workflow_run' ||
  github.event.workflow_run.name != 'verify' ||
  github.event.workflow_run.conclusion == 'failure'
```

**Only verify failures.** A green verify already reaches this workflow through
deploy, so refreshing on it buys nothing and costs a run.

That distinction is a budget decision, and this file records why it has to be.
Its own header documents a cadence cut from eight runs a day to one:

> 263 status runs at ~1 minute each is the second-largest line in this repo's
> Actions spend after `verify`, against a budget that was 90% consumed with two
> weeks of the month left.

`verify` ran **twelve times** on main today. An ungated trigger would have added
twelve status runs and undone that cut in a single session. A skipped job costs
seconds and no billable minutes.

## The gate's truth table, exercised

GitHub's `if:` is not JavaScript, but the boolean shape is identical, so it was
run rather than reasoned about:

```
ok    verify FAILED       -> must run    -> true
ok    verify succeeded    -> must skip   -> false
ok    verify cancelled    -> must skip   -> false
ok    deploy finished     -> must run    -> true
ok    drift-sentinel      -> must run    -> true
ok    daily schedule      -> must run    -> true
ok    manual dispatch     -> must run    -> true
```

The `cancelled` row matters: a cancelled verify is not a failure, and treating it
as one would fire a run on every superseded push in a rapid series. The
`schedule` and `workflow_dispatch` rows matter because a three-clause `if:` that
accidentally gates the non-`workflow_run` events would silently disable the
backstop this whole change depends on.

`check:workflows` 6/6.

## What this does not do

It does not notify anyone. It keeps the file that answers the question honest,
which is the same contract the workflow already had — the file is the surface,
not a message. Whether a red main should also reach a phone is a separate
decision with a separate cost, and it is not being made here by implication.
