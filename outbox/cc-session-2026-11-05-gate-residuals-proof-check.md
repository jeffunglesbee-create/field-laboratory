### 4. Task 7 (option A): proof-check registers no signal handler; closes 10.17b

- Premise command: a stand-in `dotnet` that signals the run's own pid from inside the first injected build, then every later build is counted. On the committed script, for SIGTERM, SIGINT and SIGHUP alike: the run took about 7 s, exit status 1 (not the handler's 130), and 6 further builds ran after the signal. The three handlers could not run: the script is one synchronous run with no `await`.
- Chosen: remove the handlers (option A), not an asynchronous rewrite (option B). The repo's recovery model is built for death without cleanup (the state on disk and the next run's heal), the handlers were provably unreachable (dead code), and B adds a second narrower recovery path for the same state. With none registered the default action stops the run at once.
- Changed: the three-line handler loop is gone; the comment above the restore, the refusal's comment and the header of `clean-source-check.mjs` that said the script traps SIGINT, SIGTERM and SIGHUP are rewritten (the one in `clean-source-check.mjs` is one comment line; nothing else in that file changed). The refusal over a hung run now says `kill PID`, not `kill -9 PID`, because a plain kill works; the clauses and entries that pinned the old rationale are re-anchored to the new advice, and the unidentified-pid clause now says "no kill" rather than "no kill -9", so it still catches a mutant that offers a kill.
- Clauses (99 to 102): one per signal, one run each: the stand-in sends the signal mid-build; the run must die of that signal, the stand-in must have been called exactly twice (the baseline and the build that signalled, so none after), the injection and the state stay, and the next run prints HEALED and leaves the target equal to the original. With the handlers put back and the clauses kept: 99/102, exactly those three fail. The refusal clauses fail 100/102 when the old advice is put back.
- Entries: three new (`proof-signal-handler-swallows-sigterm`, `-sigint`, `-sighup`, one per signal, so each clause is shown to test its own signal), two re-anchored (`proof-marker-refusal-recommends-a-checkout`, and `proof-marker-refusal-advises-a-plain-kill`, renamed `proof-marker-refusal-advises-kill-9` because its mutation is now the `kill -9` text); `proof-unconfirmed-pid-says-kill` run again. All six through the harness (`--ids`): 7/7 with the baseline, caught.
- Real `dotnet` under a signal, measured here (2026-11-05, one trial): SIGTERM sent 2 s into the batch compile; the run was dead 6 ms later with status 143, `src/Scoreboard.fs` still injected, the backups and the marker on disk. The `dotnet build` it had started was orphaned (parent pid 1) and kept running. The next run was started while that build was still alive (it was 10 s old, the batch compile takes about 11 s): it printed HEALED, its baseline compiled, and it ended 140/140 with 133 of 133 confirmed in one compile. One trial; an overlap that collides is not excluded.
- Ordering: with the handlers gone, Ctrl-C or a kill leaves the injection on disk until the next proof-check run, and `check:clean-source` meanwhile fails with a remedy that says `git checkout -- <files>`, which also discards uncommitted edits to those files.
