# Decision — field-laboratory does not get a graph tool

**Date:** 2026-09-05
**Repo:** field-laboratory
**Outcome:** **WONTDO.** No dependency added. Task #25 closed.

Asked directly: *"Can we find a graph tool for it?"* This is the same question
`decision-2026-09-04-laboratory-no-uplot.md` answered for charts, one shape
along — nodes and edges rather than a series — so it gets the same treatment:
measure the data first, decide second.

The answer is no, and the reason is not taste. **Neither candidate graph in this
repo has enough edges to need a layout engine.**

---

## The two candidates, measured

### 1. The workflow DAG

`workflow_run` is the only trigger that makes one workflow depend on another.
Extracted from every file in `.github/workflows/`:

| workflow | runs after |
|---|---|
| `deploy` | `verify` |
| `live-check` | `deploy` |
| `status` | `deploy`, `drift-sentinel`, `verify`, **`pages` — which does not exist** |

**26 workflows, 5 resolving edges and one dangling.** Two of the five are one
chain — `verify → deploy → live-check` — and the other three are `status`
reading its inputs. **18 workflows are `workflow_dispatch`-only**: isolated
nodes, each a probe run by hand with nothing downstream of it.

The dangling edge is the one thing this pass found that a diagram would have
shown and the table shows just as well: `status.yml` waits on a workflow named
`pages`, and `.github/workflows/` contains no `pages.yml`. It is inert rather
than broken — a `workflow_run` naming a workflow that does not exist simply
never fires — and it is consistent with `STATUS.md`, which reports the GitHub
Pages target as *not published, needs Pages switched on*. Left as-is: removing
it would have to be undone the day Pages is enabled, and the row in `STATUS.md`
already says what it is waiting for.

A first draft of this document said "6 edges" and "20 dispatch-only", counted by
reading the extraction output rather than by counting it. Both were wrong — the
sixth edge is the dangling one and two of the twenty also carry a `schedule` or
`push`. The numbers above come from a script that classifies each trigger set,
and the correction is left in because a decision document that quietly fixes its
own evidence is the shape this repo keeps refusing.

Six edges is a sentence. It is written as one at the top of `docs/DEPLOY.md` and
in this repo's README, and a diagram of it would carry less than the sentence
does, because the sentence can say *why* `live-check` waits for a deploy that
actually deployed.

### 2. The F# module graph

Every intra-repo `open` across `src/*.fs`:

```
$ python3 - <<'PY'   # full script in the session log
modules 32  edges 24  isolated 11
  in-degree 11  Desk
  in-degree  5  Units
  in-degree  2  Weather
  in-degree  1  Pickem, Route, Pick, Ceiling, Scout, Stats
PY
```

**32 modules, 24 edges, 11 with no edge at all.** Nine modules are depended on
by anything, and two of them account for 16 of the 24 edges. That is a star with
`Desk` at the centre and `Units` beside it — not a network. A layout engine's
whole value is finding structure a human cannot hold in their head; the
structure here is two hubs and a fringe, and the sorted table above says it
completely in nine lines.

There is also a stronger reason not to draw this one. `src/Laboratory.fsproj`
already carries the module order as an explicit, commented list, because F#
compilation is order-sensitive — a file may only reference files above it. That
list is the dependency structure, maintained by the compiler rather than by a
visualisation, and it is annotated with *why* each file sits where it does. A
generated diagram would be a second, weaker copy of a fact the build already
enforces. This repo's own rule for that situation: **is this the source, or a
copy of the source?**

## What was NOT measured, and why that is honest

Two things could be graph-shaped and were not counted:

- **The check → invariant relation.** ~65 `*-check.mjs` scripts against 17 gate
  rows. This is bipartite and `docs/gate-rows.txt` already pins it, exactly as
  the `.fsproj` pins the module order.
- **Sport → capability coverage.** A matrix, not a graph. `STATUS.md` and the
  census probes already render matrices as tables.

Neither was measured because neither could change the answer: both are small
enough to table, and both already have a maintained textual source.

## The recommendation instead

Nothing to build. `STATUS.md` is the dense scannable view this repo needed and
it already exists, generated by `.github/workflows/status.yml`, probed live
rather than read from history.

The one thing worth remembering from this pass is not about graphs at all: the
`STATUS.md` in a local checkout **can be a lie**, and was one today. Running
`node scripts/status.mjs` from a sandbox with no egress makes every live probe
fail and renders "not published" for every target — and it writes that over the
committed file. The file says so itself in its own header ("not read — rendered
outside CI"), which is the only reason it was caught. `origin/main`'s copy says
**Yes — Cloudflare Workers**, and `deploy` run 670 (2026-09-05 13:53Z) ran its
real Build, Deploy and *Confirm the deployed page actually serves* steps.

Read the committed file, not a local re-render of it. Same rule as above.
